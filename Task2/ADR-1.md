### <a name="_b7urdng99y53"></a>**Название задачи: Проектирование сценария "Просмотр истории покупок"** 
### <a name="_hjk0fkfyohdk"></a>**Автор: JointFuse**
### <a name="_uanumrh8zrui"></a>**Дата: 22.02.2026**
### <a name="_3bfxc9a45514"></a>**Контекст**
После завершения доставки покупатель может вернуться в личный кабинет, чтобы посмотреть историю покупок.
- В списке отображаются все заказы: сколько они стоили, когда были сделаны и каким способом доставлены.
- Для каждого заказа доступна подробная информация: список товаров, их количество и цена, итоговая сумма, способ доставки и оплаты, финальный статус заказа (доставлен, отменён).
- Покупатель может скачать чек, оставить отзыв о товаре или заказать его снова.
Также стоит учитывать требования к отклику всех интерфейсов приложения.

В первой версии архитектуры приложения уже заложен сервис заказов, он собирает информацию о всех когда-либо оформленных в заказ корзинах. Для обеспечения масштабирумости и производительности данного сервиса требуется переработать его систему управления данными.

|**№**|**Требование**|
| :-: | :- |
|1|Надежность|
|2|Производительность|
|3|Отказоустойчивость|

### <a name="_qmphm5d6rvi3"></a>**Решение**

Для реализации сценария «Просмотр истории покупок» выбран архитектурный подход Event Sourcing в сочетании с паттерном CQRS. В качестве хранилища событий используется KurrentDB.
Сценарий просмотра истории покупок предъявляет противоречивые требования:
- высокая скорость чтения истории заказов;
- сохранение полной и достоверной истории изменений;
- возможность восстановления состояния заказов;
- масштабирование при росте количества пользователей и заказов;
- устойчивость к сбоям.

Традиционная CRUD-модель хранения заказов фиксирует только текущее состояние сущности, что затрудняет аудит, восстановление и масштабирование операций чтения.
Подход Event Sourcing предполагает хранение последовательности событий связанных с заказом и позволяет получить полную информацию нативным методом. Текущее состояние заказа формируется путём воспроизведения событий.

CQRS разделяет систему на два независимых контура и обеспечивает:
- мгновенный возврат списка заказов;
- построение специализированных представлений;
- независимое масштабирования чтения и записи.

KurrentDB выбран как специализированное event store хранилище по следующим параметрам:
- нативная работа с потоками событий;
- гарантированная последовательность событий;
- встроенные механизмы подписок и проекций;
- высокая производительность append-only операций;
- возможность горизонтального масштабирования.

Использование KurrentDB повышает надёжность хранения истории заказов и исключает затраты на разработку проприетарного решения.

В приложении заложен контейнер MarketController для реализации паттерна API Composition на GraphQl, он уже собирает данные с других сервисов и предоставляет единую точку коммуникации с фронтендом, сервис заказов предоставляет внешний доступ к данным также через него.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

|**Подход**|**Описание**|**Преимущества**|**Недостатки**|
|:-|:-:|:-:|:-:|
|CRUD + реляционная БД|Хранение текущего состояния заказа|Простота реализации, знакомая модель|Нет полной истории изменений, сложный аудит, высокая нагрузка при аналитике|
|Audit Log поверх CRUD|Основная таблица + журнал изменений|Частичное восстановление истории|Дублирование логики, риск рассинхронизации|
|Event Sourcing без CQRS|События используются и для чтения|Единая модель|Медленные запросы, сложные выборки|
|CQRS без Event Sourcing|Разделение чтения/записи с snapshot-данными|Быстрое чтение|Потеря детальной истории изменений|
|Event Sourcing + CQRS (выбранный)|События как источник истины + отдельные read-модели|Масштабируемость, аудит, гибкость представлений|Более высокая архитектурная сложность|

**Недостатки, ограничения, риски**

1. Рост сложности системы
  - требуется понимание событийной модели;
  - усложняется отладка;
  - увеличивается порог входа для разработчиков.

2. Eventual Consistency
Read-модель обновляется асинхронно, поэтому:
  - пользователь может кратковременно видеть устаревшие данные;
  - требуется UX-обработка задержек.

3. Управление версиями событий
Изменение структуры событий требует:
  - версионирования контрактов;
  - поддержки обратной совместимости.

4. Рост объёма данных
Event sourcing хранит всю историю:
  - необходимо внедрение snapshot-механизмов;
  - требуется стратегия архивирования.

5. Сложность миграций
Изменение бизнес-логики может потребовать:
  - пересборки проекций;
  - повторного воспроизведения событий.

6. Операционные риски
  - необходимость мониторинга lag проекций;
  - контроль идемпотентности обработчиков;
  - корректная обработка повторной доставки событий.
